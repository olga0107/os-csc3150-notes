# Foundations · Stack vs Heap

**TL;DR**

- Stack 跟随函数调用保存执行状态，调用结束后撤销对应的栈帧。
- Heap 对象的生命周期由分配与释放控制，可以跨过一次函数返回。
- Pointer 本身和它指向的对象是两个对象，必须分别判断谁仍然存活。

## 1. Stack · 函数调用为什么适合用栈？

**核心问题：A 调用 B 后，怎样记住 A 还没做完的工作？**

每次调用要保留一些信息：参数、局部值，以及结束后该回哪里继续。典型实现把这些信息放在 **stack frame（栈帧）** 中。

```text
main 调用 A，A 再调用 B：

栈顶 → B 的 frame：B 的局部状态，返回 A 的位置
       A 的 frame：A 的局部状态，返回 main 的位置
       main 的 frame
```

1. Main 调用 A：A 的调用状态加入栈中。
2. A 调用 B：A 暂时停下，它的 frame 留着，再加入 B 的 frame。
3. B 返回：撤销 B 的 frame，回到 A，A 的局部值仍在。
4. A 返回：撤销 A 的 frame，再回到 main。

最后进入的调用最先结束，这就是 **LIFO（last in, first out，后进先出）**。SP（stack pointer）记录当前栈位置。

> 💡 栈中保存的是这次调用的状态，不是把整个函数代码复制一遍。两次调用可以执行同一份代码，同时拥有不同的参数和局部对象。

具体的参数传递和保存方式由编译器及调用约定决定，局部值也可能在寄存器中。本节先用栈帧模型理解调用关系。

## 2. Heap · 数据需要比函数活得更久怎么办？

**核心问题：函数返回了，它创建的数据能不能留给调用者？**

```c
int *make_number(void) {
    int *p = malloc(sizeof *p);
    if (p != NULL) *p = 42;
    return p;
}
```

需要包含 `<stdlib.h>`。这里有两个对象：

```text
函数执行中：
局部变量 p [地址] ──────► 分配的 int [42]
       生命周期较短             生命周期由 free 结束
```

按时间追踪：

1. `malloc` 成功，创建一个可存 int 的对象。
2. 局部指针 p 保存它的地址，`*p = 42` 把 42 写入新对象。
3. `return p` 把**地址的值**交给调用者。
4. 函数结束，局部 p 失效；malloc 创建的对象尚未 free，仍然存在。
5. 调用者保存收到的地址，继续访问该对象，最终负责释放。

**`return p` 与 `return &local` 不同：** 前者可以交回仍存活的 heap 对象地址；后者指向一个在返回时就失效的局部对象。

### 调用者怎样接住并释放？

```c
int *result = make_number();
if (result == NULL) {
    return EXIT_FAILURE;
}
printf("%d\n", *result);
free(result);
result = NULL;
```

- `result` 保存函数交回的地址，不是原来局部变量 p 本身。
- 先检查 NULL，再解引用；分配失败时没有合法 int 可读。
- `free(result)` 结束分配对象的生命周期，之后不再读写它。
- `result = NULL` 只清空这个指针变量，避免继续误用；它不负责释放内存。

## 3. 对象归属与生命周期放在一起看

**核心问题：一行代码里，哪些东西在 stack，哪些在 heap？**

| 对象 | 常见位置 | 什么时候结束生命周期？ |
|---|---|---|
| `int local = 3` 中的 local | Stack 或寄存器 | 所在作用域的执行结束 |
| `int *p = malloc(...)` 中的 p | Stack 或寄存器 | 局部 p 所在作用域的执行结束 |
| 上一行分配的对象 | Heap | 调用 free 时 |
| Global / static 对象 | 静态存储区域 | 程序执行结束 |

**选择时先问两个问题：数据要活多久，最后谁负责清理？**

- 只在当前调用中使用的小对象，通常直接用局部变量。
- 需要在函数返回后继续存在的数据，可以由调用者提供存储，也可以动态分配。
- 不要只按“大小是否在运行时确定”判断。一些 C 实现支持变长局部数组，它们仍不会自动活过函数返回。

内存分配里的 heap 与优先队列使用的 heap 数据结构不是同一个概念。

### Heap 向上、stack 向下，是固定规则吗？

这种示意强调：两部分随使用增长，利用中间空闲空间。真实布局还可能有多个线程栈、多个分配区域。

- C 不保证连续两次 malloc 返回相邻地址。
- 每个线程有自己的调用栈，但同进程的地址空间仍然共享。
- 把栈对象地址交给另一线程时，原对象必须一直存活到对方用完，还要协调冲突访问。

## 4. 释放后的地址：为什么 p 设为 NULL 还不够？

**核心问题：同一对象被多个指针指向，free 会把它们都清空吗？**

```c
int *p = malloc(sizeof *p);
if (p == NULL) return EXIT_FAILURE;
int *q = p;
free(p);
p = NULL;
// 此后不能再用 *q，也不能再次 free(q)。
```

1. `p` 和 `q` 原先保存同一个地址，指向同一分配对象。
2. Free 释放这个对象，不会逐个查找并清空所有指针。
3. `p` 被设为 NULL，但 q 仍保存旧地址，成为 dangling pointer（悬空指针）。
4. 要保证安全，必须在释放前确保所有使用者都已用完，而不是只改一份指针。

| 问题 | 含义 | 如何理解？ |
|---|---|---|
| Allocation failure | 分配失败 | Malloc 返回 NULL，没有拿到所需对象 |
| Memory leak | 内存泄漏 | 对象不再需要，却失去或忘记释放它 |
| Use-after-free | 释放后使用 | 对象已失效，还沿旧地址读写 |
| Double free | 重复释放 | 同一次分配被释放两遍 |
| Buffer overflow | 缓冲区越界 | 访问超出对象范围，stack、heap 都可能发生 |
| Stack exhaustion | 栈空间耗尽 | 调用过深或局部对象过大，超出可用栈空间 |

**Heap 也有容量限制，放在 heap 并不能消除越界。** 分配够不够、索引是否在范围内、对象是否仍存活，是不同检查。

## Demo · 函数返回后继续读取 heap 对象

```sh
cc -std=c11 -Wall -Wextra demos/lec02/heap_lifetime.c -o /tmp/os-heap-lifetime
/tmp/os-heap-lifetime
```

实际输出：

```text
after function returns: 42
released; result reset to NULL
```

第一行说明 make_number 已经返回，但分配对象仍可读取。第二行发生在 free 和指针置空之后，此时程序没有再解引用旧地址。

递归栈的完整推演见 [Lecture 3：独立调用栈](../notes/lec03-thread-process.md#独立调用栈-递归推演)：调用顺序是 `A(1) → B → C → A(2)`，输出顺序却是 2、1，因为最内层先执行完。

## Self-check

1. 为什么 B 返回后，A 的局部值还在？
2. 局部 p 失效，为什么 malloc 的对象仍可能存在？
3. `free(p); p = NULL;` 是否让所有别名指针安全？
4. 放到 heap 上能否避免越界？
5. 函数需要把结果交给调用者，是否一定要 malloc？

**A1.** A 的调用尚未结束，A 的 frame 留在栈中。B 返回只撤销 B 的调用状态，然后恢复 A。

**A2.** 它们是两个不同对象。`p` 的生命周期由作用域控制，分配对象则持续到 free；返回地址值允许调用者继续找到后者。

**A3.** 不能。其他指针仍可能保存旧地址；释放前要确认没有使用者还需要该对象。

**A4.** 不能。每个分配对象都有边界，超过边界访问仍是错误。

**A5.** 不一定。可以把值直接返回，也可以让调用者先准备对象，再把地址传入供函数写结果。需要动态分配时，再明确分配失败和释放责任。
