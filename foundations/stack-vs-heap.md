# 基础补充 · Stack vs Heap：内存里的两段到底干什么

> 对应主线：[Lecture 2 §5 Address Space](../notes/lec02-concepts.md)

**TL;DR**: 内存布局里的 stack 和 heap 与数据结构课上的栈/堆**不是一回事**。stack 段管"函数的一生"（调用时自动压栈、返回自动弹出），heap 段管"数据的一生"（`malloc` 租、`free` 还，活多久你说了算）。

***

## 0. 先解除最大的误会：两对同名概念

数据结构课上的 stack（LIFO 栈）和 heap（堆/优先队列），跟内存布局里的 stack、heap 是两个世界：

* 内存里的 **stack 段**确实是后进先出的栈，名字名副其实。
* 内存里的 **heap 段跟堆数据结构毫无关系**，它只是一块自由内存池，叫 heap 纯属历史命名巧合。

理解内存布局不需要任何堆数据结构的知识，从零开始即可。

## 1. Stack 段：为"函数调用"而生

**它解决的问题**：程序运行就是不断的函数调函数。每次调用都需要一小块内存放局部变量、参数、返回地址；函数一结束，这块内存就没用了。

**工作方式**像一摞盘子，`main()` 调用 `f()`，`f()` 调用 `g()` 时：

```
高地址  ┌─────────────┐
        │ main 的 frame │ ← main 的局部变量、返回地址
        ├─────────────┤
        │ f() 的 frame  │
        ├─────────────┤
        │ g() 的 frame  │ ← SP（栈顶指针）在这
低地址  └─────────────┘   注意：stack 向低地址生长
```

* `g()` 返回，它的 frame 直接弹出（SP 往回挪一格）。**后进先出，全自动**。
* 分配和释放只是移动 SP 指针，所以**极快**。
* 代价：大小有限（默认几 MB）。无限递归会把栈压爆，这就是 **stack overflow** 的字面来源。
* 生命周期铁律：**局部变量随函数返回立刻失效**。"返回局部变量的地址"是 C 语言经典 bug，那个地址随时会被下一次函数调用覆盖。

## 2. Heap 段：为"我自己说了算"而生

**它解决的问题**：有些数据的生命周期不跟着函数走。比如函数创建了一个对象，返回后还要长期用；或者你需要**运行时才确定大小**的内存（读入任意长度的文件）。栈做不到这些。

**工作方式**像租储物柜：

* `malloc(100)`：向管理员（内存分配器 allocator）租 100 字节，它从空闲池划一块，把地址给你。
* 这块内存**一直有效，直到你 `free()` 还回去**。函数返回了它还在，谁拿到地址谁就能用。
* 代价：分配器要记账，比栈慢；忘了 `free` 就**内存泄漏**；`free` 两次（double free）或还了之后继续用（use-after-free）都是大坑。

## 3. 实机演示

代码见 `demos/lec02/stack-vs-heap.c`，一次运行同时看两种行为：

```
main   的局部变量: 0x16d852638
level2 的局部变量: 0x16d8525ec    ← 比 main 低
level3 的局部变量: 0x16d8525cc    ← 比 level2 还低

h1 = malloc(100):  0x1025ddae0
h2 = malloc(100):  0x1025ddb50
h3 = malloc(100):  0x1025ddbc0   （在 free(h1) 之后分配）
```

**上半部分（stack）**：每深一层函数调用，局部变量的地址就更低一点。这直接证实了布局图里 stack 朝下的箭头：调用越深，frame 越往低地址压。level3 返回后 frame 弹掉，`0x…5cc` 立刻作废。

**下半部分（heap）**：

1. heap 地址（`0x102…`）和 stack 地址（`0x16d…`）差着数量级，正好对应布局图：heap 在低处向上长，stack 在高处向下长，中间隔着巨大空隙。
2. 三块内存紧邻分配，malloc 从池子里顺序划地。
3. `free(h1)` 之后再 `malloc` 得到的 h3 是 `bc0`，并没有复用 h1 的 `ae0`：回收的块何时再利用由分配器策略决定，不像栈那样机械弹栈。所以 `free` 之后的地址不能再碰，你不知道它什么时候会被发给别人。

## 4. 对照表

| | Stack 段 | Heap 段 |
|---|---|---|
| 存什么 | 函数局部变量、参数、返回地址 | `malloc` 出来的动态内存 |
| 谁管分配 | 编译器自动（移动 SP） | 你手动 `malloc` / `free` |
| 生命周期 | 跟函数调用绑定，返回即失效 | 你说了算，`free` 前一直有效 |
| 速度 | 极快（挪一下指针） | 较慢（分配器要记账） |
| 大小限制 | 小（几 MB，爆了即 stack overflow） | 大（内存够就能租） |
| 经典坑 | 返回局部变量的指针 | 泄漏、double free、use-after-free |

一句话记忆：**stack 管"函数的一生"，heap 管"数据的一生"**。函数活得短，数据想活多久都行，所以它们住在两个方向相反的段里。

## 5. Self-check

1. 为什么"函数返回局部变量的指针"是 bug？用 frame 弹出解释。
2. 什么需求必须用 heap 而不能用 stack？举两个。
3. Stack overflow 是怎么发生的？为什么 heap 没有对应的"heap overflow"？

<br />

**A1.** 局部变量存在函数的 frame 里，函数返回时 frame 弹出、SP 回移，那块内存标记为可用，下一次函数调用会原地覆盖它。返回的指针指向一块随时会被改写的内存，读到的值不再受控制。

**A2.** ① 生命周期跨函数的数据：函数创建、返回后还要继续用的对象。② 大小运行时才知道的内存：比如按文件实际大小分配缓冲区。栈在这两种情况下要么"活不够久"，要么"大小必须在编译期可知且受限于栈容量"。

**A3.** 递归或调用链太深，frame 一路向低地址压，耗尽预留的栈空间即 stack overflow。Heap 没有对应的固定边界，它面对的是整个空闲内存池，`malloc` 失败是返回 `NULL`（可以检查、可以处理），而不是灾难性地撞上硬边界。所以课件示例代码里才有 `if (heap_var == NULL)` 的检查。
